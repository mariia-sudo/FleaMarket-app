# FleaMarket

A local second-hand marketplace for the US, priced in an in-app currency instead of
dollars. Buyers top up coins with a card; sellers get paid in coins and can cash out
to their bank account.

Two pieces:

| | |
|---|---|
| `server/` | Node + Express + Prisma API. Owns the double-entry coin ledger. |
| `mobile/` | Expo (React Native) app for iOS and Android. |

---

## Run it

Two terminals.

**API** — creates a SQLite database, fills it with demo data, starts on port 4000:

```bash
cd server && npm install && npm run reset && npm run dev
```

**App** — opens in the iOS simulator:

```bash
cd mobile && npm install && npm run ios
```

### On a physical phone

Two files hold the API address, and both matter:

- `server/.env` → `PUBLIC_URL` — uploaded photo URLs are built from it, so if it says
  `localhost` the photos won't load on a phone.
- `mobile/.env` → `EXPO_PUBLIC_API_URL` — baked into the app at build time.

Both should point at the machine running the API, e.g. `http://192.168.1.35:4000`.
In a *development* build the app can work the address out from the Expo dev server, so
`mobile/.env` is optional there — but a Release build has no dev server to ask.

**Quickest route (Expo Go).** Install Expo Go from the App Store, run
`npx expo start` and scan the QR. No signing, no build, but the app lives inside Expo Go
rather than having its own icon.

**Real installed app.** Plug the phone in, trust the Mac, then:

```bash
cd mobile && npx expo run:ios --device --configuration Release
```

Release rather than debug, so the JS is bundled into the app and it runs without Metro.
It still needs the API to be reachable.

Two things that will bite on a fresh machine:

- CocoaPods on newer Ruby dies with `Unicode Normalization not appropriate for
  ASCII-8BIT`. Fix by running the build with `LANG=en_US.UTF-8 LC_ALL=en_US.UTF-8`.
- `ios/` is generated by `expo prebuild` and is gitignored. The signing team is written
  into `ios/FleaMarket.xcodeproj/project.pbxproj` as `DEVELOPMENT_TEAM`, which means a
  re-run of `expo prebuild --clean` wipes it. Set it again with:

  ```bash
  cd mobile/ios && perl -pi -e 's/^(\s+)PRODUCT_BUNDLE_IDENTIFIER = (.*);$/$1PRODUCT_BUNDLE_IDENTIFIER = $2;\n$1DEVELOPMENT_TEAM = J9365K4AUH;\n$1CODE_SIGN_STYLE = Automatic;/' FleaMarket.xcodeproj/project.pbxproj
  ```

  `J9365K4AUH` is a **free** personal team. It installs fine on your own phone, but the
  provisioning profile lives 7 days and then the app stops opening until you rebuild.

  TestFlight and the App Store need a paid Apple Developer Program membership. There is
  one on this machine — team `FX28Z4P756` — but switching to it needs more than changing
  this string: Xcode must have that Apple ID signed in under Settings → Accounts,
  otherwise the build fails with `No Account for Team`. A certificate sitting in the
  keychain is not enough, because Xcode has to talk to Apple to create the profile.

- Xcode won't create a provisioning profile for a new bundle id unless you ask it to, so
  a first build needs `-allowProvisioningUpdates`. `expo run:ios` doesn't pass it, which
  is why the build below goes through `xcodebuild` directly:

  ```bash
  cd mobile/ios && LANG=en_US.UTF-8 xcodebuild -workspace FleaMarket.xcworkspace \
    -scheme FleaMarket -configuration Release -destination "id=<device-udid>" \
    -derivedDataPath ./build -allowProvisioningUpdates build
  xcrun devicectl device install app --device <device-udid> \
    ./build/Build/Products/Release-iphoneos/FleaMarket.app
  ```

  Get the UDID from `xcrun devicectl list devices`. The first launch on the phone needs
  the certificate trusted under Settings → General → VPN & Device Management, and the app
  will ask for Local Network permission — both are required for it to reach the API.

- The bundle id must be globally unique across all of Apple. `com.fleamarket.app` was
  already taken, which is why this is `com.mashaegorova.fleamarket`.

The app only works while it can reach the API — that is, on the same network as the Mac,
with `npm run dev` running in `server/`. To use it anywhere, deploy the API (see below).

## How the money works

**Everything is integers.** A coin is stored as 100 minor units, exactly like dollars
and cents. `priceCoins: 2500` is 25 coins. Nothing anywhere uses floating point for
money. The conversions live in `server/src/money.ts` and `mobile/src/money.ts`.

**Every movement is double-entry.** There is no `balance` column anywhere. A balance is
the sum of an account's ledger entries, and every transaction writes entries that sum
to exactly zero — enforced in code, on every write (`server/src/ledger.ts`). That's what
makes it possible to answer "where did my coins go" a year later, and it's why `npm run
audit` can prove the whole system balances.

```
Top up      SYSTEM_MINT  −50   →  user        +50    coins come into existence
Buy         buyer        −65   →  SYSTEM_ESCROW +65   coins leave the buyer, nobody has them
Confirm     SYSTEM_ESCROW −65  →  seller      +65    handoff confirmed, seller paid
Cancel      SYSTEM_ESCROW −65  →  buyer       +65    coins go home
Cash out    user        −100   →  SYSTEM_PAYOUT +100  coins burned, dollars sent
```

System accounts may go negative. `SYSTEM_MINT` sitting at −41800 means 418 coins exist.

**Escrow is the product.** When a buyer taps Buy, the coins leave their wallet but do
*not* reach the seller — they sit in `SYSTEM_ESCROW` until the buyer confirms they
physically have the item. Either side can cancel until then. This is the honest answer
to "why not just use Venmo": on Craigslist, whoever moves first is exposed.

### Revenue

Set in `server/src/money.ts`. All of it is a lever.

- **Buy coins:** $1.00 per coin, with bonus coins on bigger packs (up to +8%).
- **Sell:** the seller keeps 100%. `PLATFORM_FEE_BPS = 0`.
- **Cash out:** 1 coin pays $0.85.

The platform earns on the spread, not on the sale. Someone who puts in $100 gets 108
coins; if every coin is eventually cashed out we pay $91.80 and keep $8.20 gross (~8%),
of which Stripe takes roughly half. Coins that keep circulating inside the market never
cost us the spread at all — which is why "spend what you earned here" is worth pushing
in the UI.

"0% seller fees" is also the marketing. Mercari takes ~10%, Poshmark 20%.

### Audit

```bash
cd server && npm run audit
```

Prints every account and fails loudly if the ledger doesn't sum to zero. Run it after
touching `ledger.ts`, and on a schedule in production.

## Legal shape — read before launch

Three things constrain this product. They're already handled in the code, but they'll
determine what you can and can't change.

**1. Apple won't let you sell these coins through in-app purchase.** App Store guideline
3.1.3(e) forbids IAP for anything redeemable against physical goods, and these coins buy
used furniture. Top-ups therefore go through Stripe Checkout in a browser sheet, which
is both compliant and 30% cheaper. Never move this to `expo-in-app-purchases`.

**2. Money transmission.** Selling a currency for dollars, moving it between users, and
paying it back out in dollars is regulated money transmission in the US — federal FinCEN
MSB registration plus per-state licensing, which realistically costs millions and years.
This is avoided by never holding customer funds: **Stripe Connect** is the licensed
party, it runs KYC on each seller, and a cash-out is a Stripe transfer from the platform
to the seller's own connected account. That is why `payoutsEnabled` is only ever set by
the `account.updated` webhook and never by the client.

Get this reviewed by a fintech lawyer before taking real money. The architecture is the
standard marketplace one, but "standard" is not "cleared".

**3. Unclaimed property / gift card law.** Some states treat prepaid balances as
property that must eventually be returned to the holder. Coins here are cashable, which
is the safer side of that line — but it's another reason not to switch to a
"credits, no withdrawals" model without advice.

## Stripe

The app runs fully without Stripe keys. `server/.env` with empty keys puts the wallet in
**sandbox mode**: top-ups credit coins instantly, payouts are marked paid, no money
moves. Everything else — escrow, orders, the ledger — is real.

To exercise the real flow, put Stripe **test** keys in `server/.env` and run:

```bash
stripe listen --forward-to localhost:4000/stripe/webhook
```

Webhooks handled in `server/src/routes/stripeWebhook.ts`:

- `checkout.session.completed` → credit the coins (idempotent; Stripe retries)
- `checkout.session.expired` → mark the top-up failed
- `account.updated` → flip `payoutsEnabled` after Connect onboarding

```
PATCH  /auth/me

GET    /listings/favorites
POST   /listings
PATCH  /listings/:id

POST   /orders                 buy — moves coins into escrow
GET    /orders                 ?role=buying|selling|all
GET    /orders/:id

POST   /orders/:id/cancel      either side — refunds escrow

GET    /wallet                 balance, packs, rates, payout status

GET    /health                 public

```

## What this base does not have yet

Deliberate omissions, roughly in the order they'll start hurting:

- **Account deletion.** Apple requires any app that lets you create an account to let you
  delete it from inside the app (guideline 5.1.1(v)). There is no such endpoint or
  screen, so this is a guaranteed App Store rejection. Note it isn't a plain `DELETE FROM
  users`: ledger entries and completed orders are financial records the other party is
  entitled to, so deletion has to anonymise the user rather than remove the rows.
- **Reviews and ratings.** A used-goods marketplace runs on trust and there is currently
  none. This is the first thing to build.
- **Push notifications.** Chat polls every 4 seconds while the screen is open, and
  nothing reaches you when the app is closed.
- **Disputes.** If a buyer never confirms, the coins sit in escrow forever. Needs an
  auto-release timer and a way for a human to intervene.
- **Rate limiting and abuse controls.** Nothing stops a script from creating accounts or
  spamming listings.
- **Email verification and password reset.**
- **Image moderation.** Anyone can upload anything.
- **Postgres.** SQLite is fine for development and wrong for production. The schema is
  written to port cleanly; the one thing to fix on the way is the read-then-write balance
  check in `ledger.ts`, which needs `SELECT … FOR UPDATE` under real concurrency.
- **Dark mode.** The app is light-only.
- **Tests.** `server/scripts/audit.ts` proves the ledger balances, which is the invariant
  that matters most, but there are no unit tests.
